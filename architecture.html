How Agri-Cal works

A React calendar talks to an Express server. The server manages records, builds assistant context, and calls external APIs.

Three main request paths

01 / Manual calendar change

Form → record → calendar

  1. The user submits an event form.
  2. The browser sends a request to /api/events.
  3. Express validates creation data and calls storage.
  4. Memory storage returns the saved event.
  5. Query invalidation requests fresh events.
  6. CalendarContext expands recurrence for the views.

The record does not survive a server restart.

02 / Assistant request

Message → context → tools

  1. A chat screen sends a conversation message.
  2. The server reads events and fetches weather.
  3. It builds a prompt and calls OpenAI.
  4. The first tool call can read or change records.
  5. A second model request creates the final reply.
  6. The server saves the conversation and returns it.

Location input, follow-up tools, and event refresh have gaps. Reply scanning can add another write.

03 / Weather display

Location → forecast → cards

  1. LocationContext supplies a selected location.
  2. The weather hook calls /api/weather.
  3. The server geocodes the location.
  4. Open-Meteo returns measurements and forecast data.
  5. The adapter caches and formats the response.
  6. The hook passes data to weather cards.

The hook reads forecasts; the route returns current and forecast. Units also need correction.

Source map and limits

Browser entry points and state

main.tsx mounts the providers. App.tsx mounts pages and floating chat. CalendarContext.tsx owns calendar state. LocationContext.tsx owns location state. queryClient.ts manages requests and cache defaults.

Server, storage, and external APIs

server/index.ts configures Express and sessions. routes.ts contains API routes, context, model calls, and tools. storage.ts selects memory storage. schema.ts defines record shapes and database tables. openWeatherApi.ts actually calls Open-Meteo. perplexityApi.ts calls the search provider.

Development and production serving

The server defaults to port 3000. Development can serve Vite through Express. The separate client command uses port 5001 and proxies API requests to port 3000. Production serves built files from dist/public.

The separate client Vite config still imports Replit plugins absent from the package manifest. The root Vite config uses a different plugin list. These describe configured paths, not verified startup.
