The vision, restated so we can measure against it

Three pillars, in the owner's words and examples:

Pillar 1

It knows the farm

The program holds immense context about a farmer's operation: area and location, crops, equipment, tractors, buildings, staff, and possibly years of historical data — or none at all, and it still works. Every answer and plan is grounded in that knowledge.

Pillar 2

It researches and builds intense plans

The farmer says "I want to plant a vegetable garden," "manage five acres of sorghum," or "I need to make insecticide by fermenting tobacco." The system does real research with verified results, reasons about timings, gestation periods and conditions, then generates many interlocking calendar events, each carrying deep instructions and SOP support in its notes.

Pillar 3

It manages proactively

An agent watches the calendar, the weather, and conflicts. Five days before a scheduled planting it notices high rain probability, brings it to the farmer, and has a pre-made change ready — then applies it on approval. A very smart farm manager operating through a calendar interface.

The one-sentence gap: today the assistant can take dictation and write correct events when asked — but it does not know the farm, its research is wired yet flawed, it cannot compose a linked plan at scale, and nothing in the system ever acts unless the farmer is watching a page.

What is solid right now (verified this review)

The September reliability pass fixed the failures documented in the prior review. In the current working tree:

  • Data survives and is private. PostgreSQL via Drizzle (in-memory only under explicit MEM_STORAGE=1); every private route and every assistant tool checks the session user and record ownership; strict schemas reject ownership/ID tampering; bcrypt auth, persistent sessions, rate limiting, helmet.
  • The calendar is semantically correct. Day/week/month/year views share one query; recurrence expands for the visible range (month-end clamp, DST-safe, no 500-iteration loss); ICS import is validated and transactional with UID-based duplicate skip; export round-trips.
  • Weather is real and honest. Open-Meteo in °F/mph/inches, current + 7-day forecast, 10-minute cache, geocoding with Nominatim fallback, provider timezone handled; unavailable data is labeled unavailable.
  • The assistant writes only through validated server tools. One model (CHAT_MODEL), a bounded tool loop that executes every returned call, structured mutation results the client uses to refresh, honest partial-failure reporting, and a fresh per-message context (farm time, timezone, advice mode, resolved location, hemisphere-correct season, next-7-day occurrences, mentioned projects). The old reply-scanning duplicate-write path is gone.
  • Regression tests exist and pass (ICS, recurrence, tool schemas, weather mapping): 23/23, TypeScript clean.
But note: this entire pass is uncommitted (30+ modified files on release/v2), the SPEC.md browser scenario has not been run, and neither gpt-4.1-mini nor the Perplexity model has been verified against a live account. Bank this work first — see Phase 0.

Pillar 1 — The program knows the farm

What exists
  • One location per user (GPS or manual, with confidence and persistence) plus general/local advice mode; the server validates it, geocodes it, and injects farm time, season, and location into every assistant request (server/routes.ts:940–1028).
  • The assistant sees the next 7 days of the user's calendar (recurrence-expanded, with event IDs) and details of any project whose name appears in the message (routes.ts:976–1027).
  • Files and documents tables exist, both linkable to projects; the assistant can list files and create list note/plan/report documents.
  • Projects act as loose containers (name, description, status, dates, color) that group events.
What is missing
  • No farm entity model at all. shared/schema.ts has users, projects, events, conversations, files, documents — nothing for fields/plots/acres, soil, crops and varieties in the ground, equipment, tractors, buildings, or staff. There is no farm profile page or settings UI anywhere in the client.
  • No long-term memory or history. No yield records, treatment logs, or field history — the "years of data" concept does not exist. Context is rebuilt thin for each message; across conversations the assistant retains only the raw chat log.
  • Documents are invisible. The assistant can write plans and notes the farmer can never open — there is no documents page; only a query-invalidation hint references the API (client/src/App.tsx:15–26).
  • Files are a facade. The read_user_file tool does not read content — it returns the string "File content would be read from: {path}" (routes.ts:824). Uploads are read as text client-side and stuffed into JSON metadata, mangling PDF/XLSX (FileUpload.tsx:79–109). The Files page claims AI analysis that cannot happen.
  • The weather_cache table is unused (the live cache is an in-memory Map, openWeatherApi.ts:10) — so even weather history, which the future agent will need, is not persisted.
What to build
  • Farm profile schema + settings UI: farms, fields (name, acres, soil, notes), crops/plantings, equipment, buildings, staff. All optional — the "maybe no data" case is simply an empty profile the assistant acknowledges.
  • Context injection: include the farm profile (and demand-driven retrieval over documents/files) in the per-message context block so every answer is grounded in this farm.
  • Documents page: list, read (markdown), tag, link to projects/events. The backend already exists.
  • Make files real: read_user_file returns actual stored content for text formats and honest failure for binary; move to real storage with multipart upload.
  • Persist weather history into the existing weather_cache table so later pillars can reason over observed conditions.

Pillar 2 — Real research → intense, multi-event plans

What exists
  • A search_web tool wired to Perplexity with citations, callable repeatedly inside the bounded tool loop; a get_weather tool; create/update/delete/search event tools; get_or_create_project; create_user_document for plan documents. All validated and ownership-checked (routes.ts:641–927).
  • The loop can and does create multiple events per request, and reports every saved ID.
  • A seed of one-click planning: the EventModal "Generate Calendar" button asks the model for a JSON array of events and creates them (EventModal.tsx:303–404), plus a per-event "Task Advice" button.
  • ICS import lets a farmer bring in a plan built elsewhere.
What is missing

Research quality

  • search_recency_filter: "month" (perplexityApi.ts:70) restricts results to roughly the last month — actively wrong for evergreen agronomy (fermenting tobacco, sorghum maturity windows, spacing charts) and for anything seasonal.
  • Small, dated model (llama-3.1-sonar-small-128k-online) with max_tokens: 500 — deep answers get truncated.
  • Research failures masquerade as success. searchWeb catches its own errors and returns an error string; the tool then reports success: true (perplexityApi.ts:93–97, routes.ts:642–645). Without PERPLEXITY_API_KEY, the assistant "researches" into an error message and may still plan confidently. No cross-checking, no source verification, no citations shown to the user.

Plan capability

  • No Plan/SOP entity. A "plan" is N independent events: no dependency links, no relative offsets ("transplant +3 weeks," "scout weekly for 8 weeks"), no gestation/maturity windows, no variety/rate/coverage metadata, no regenerate or shift-the-whole-plan operation.
  • Scale ceiling. Each event is one tool call; the loop allows 8 model round-trips (modelConfig.ts:15). A 20–30 event garden plan can exhaust the budget mid-plan. No batch create_plan tool, no transactional commit.
  • The assistant cannot create recurring or all-day events (hardcoded false, routes.ts:676–679; absent from toolSchemas.ts:53–61).
  • No preview or approval. Events write immediately on chat; nothing shows "here is the plan about to be created."
  • Notes are not SOPs. Description is a 3-row plain textarea, rendered as plain text; no structure (materials, steps, dosages, safety, contingencies), no markdown rendering in views.
  • The client "Generate Calendar" path is fragile: regex-extracts JSON out of a markdown reply (EventModal.tsx:324), forces every event to 9 AM and checkWeather: true (:359, :375), writes immediately with no preview, and bypasses server-side plan validation entirely.
What to build
  • Fix research first (cheap, high impact): drop or parameterize the recency filter; move to a current Sonar model; raise the token budget; make failures propagate as tool failures so the assistant says "research unavailable" instead of planning on an error string; surface citations in the reply.
  • A real plan generator: a server-side create_plan tool that accepts a batch — events with relative offsets and dependency links, a plan document with sources, and a project — committed transactionally. Raise or special-case the loop budget for plan requests.
  • Plan review UI: draft plan → event list with dates and full notes → approve / edit / reject → commit. This matches the owner's intent (intense plans the user can inspect) and protects against a bad research pass.
  • SOP-grade notes: markdown descriptions with per-activity templates (steps, materials, rates, safety, "why this date"), rendered as markdown in event views.
  • Extend assistant event tools with recurrence and all-day support.
  • Retire the client-side Generate Calendar in favor of the server path (keep the button, change what it calls).
  • Optional but valuable: a crop/region knowledge layer (hardiness zone, frost dates, growing degree days) to sanity-check research against the farm's location.

Pillar 3 — The proactive farm manager

What exists
  • Events carry a checkWeather flag, and GET /api/events/weather-dependent already joins flagged events with the forecast (routes.ts:329–355) — but only the Weather page consumes it, and only when the user visits (Weather.tsx:285–339).
  • Client-side threshold banners (precip > 1", temp > 95°F / < 32°F, wind > 20 mph) on forecast cards.
  • The assistant can reschedule events in chat when the farmer thinks to ask — reactive, not proactive.
What is missing
  • Nothing ever runs on its own. There is no scheduler, cron, or job runner of any kind in the server (verified — no scheduling code exists). Even with the app open, no page cross-references forecast vs. upcoming events automatically.
  • No detection engine. The exact scenario — planting Tuesday, 80% rain five days out — is computable today from existing data (events + checkWeather + 7-day forecast) but nothing computes it.
  • No notifications. The bell button is decorative — no click handler, hardcoded unread dot (layout/Header.tsx). No inbox, no email, no push. ws sits unused in package.json.
  • No proposal workflow. No suggestion entity, no pre-made change sets ("move to Thursday 9 AM"), no approve/decline, no atomic apply of approved changes, no memory of dismissed suggestions.
  • No conflict detection — overlaps, equipment/staff double-booking (also blocked until Pillar 1 entities exist).
What to build
  • A job runner (e.g. node-cron) with a first job: weather watch — for each user with a location, join checkWeather events inside the forecast horizon against the forecast and evaluate per-activity rules (rain probability for planting/spraying, wind for spraying, frost for transplanting, etc.).
  • Proposals: a proposals table holding a drafted change set (event moves/cancellations, rationale, forecast evidence), APIs, and UI — the agent's "pre-made change ready to go." Approve → apply atomically; decline → record so it is not re-raised.
  • A real notification bell: in-app inbox fed by proposals (poll or the already-installed ws), optional email digest for farmers who are not daily users.
  • Escalation into chat: the agent posts its reasoning (with forecast data as evidence) into the assistant conversation, so the farmer can converse about the suggestion.
  • Conflict rules once equipment/staff entities exist.

Note: SPEC.md line 15 deliberately excluded background scheduling and agents from the reliability pass — correct at the time, and it is why this pillar is greenfield: there is nothing to repair, only to build, on a now-solid foundation.

Build order — foundation first, then memory, then plans, then the manager

Phase 0
days

Bank the foundation

Run the SPEC.md browser scenario end-to-end (login → location → weather-aware task → verify ID → restart). Verify CHAT_MODEL and the Perplexity key/model against the live accounts. Apply the three P1 research/file fixes (recency filter, failure propagation, real file reads). Commit the reliability pass.

Phase 1
1–2 weeks

The farm's memory (Pillar 1)

Farm profile schema (fields, crops, equipment, buildings, staff — all optional) + settings UI + ownership-checked APIs. Inject the profile into assistant context. Documents page. Real file reads and storage. Persist weather history. Exit test: ask the assistant "what's on the north 40?" and get an answer grounded in stored data; with an empty profile it says so instead of inventing.

Phase 2
2–4 weeks

Research-grade plans (Pillar 2)

Verified research (current model, no recency bias, citations surfaced, failures honest). Server-side create_plan tool: batch events with dependencies and offsets, plan document with sources, project grouping, transactional commit, loop budget sized for 30+ events. Plan review/approval UI. Markdown SOP notes rendered in views. Recurrence/all-day in assistant tools. Retire the client generator. Exit test: "plan a vegetable garden" produces a reviewable 20+ event plan whose dates chain from research and whose notes are real instructions.

Phase 3
2–4 weeks

The proactive manager (Pillar 3)

Job runner + weather watch over checkWeather events and forecasts. Proposals with pre-made change sets, rationale, and forecast evidence; approve/decline with atomic apply and dismissal memory. Real notification inbox (bell → proposals; ws already in the dependencies), optional email digest. Exit test: schedule a planting inside a rain window in the forecast; within one job cycle a proposal exists, the bell shows it, approval moves the event.

Phase 4
ongoing

Depth and polish

Multi-year history and yield logs; frost-date / growing-degree intelligence; equipment and staff conflict scheduling; drag-and-drop rescheduling; mobile polish; plan templates reusable across seasons.

Decisions to make before building

  • One farm per user, or many? Affects the profile schema's top level (the current vision implies one farm per account — simplest).
  • Research provider: keep Perplexity (fix config) or move to OpenAI web-search tooling for one fewer key/vendor.
  • Plan writes are approval-gated (owner's intent) — chat-side single events stay direct; batch plans always preview. Confirm.
  • Notification channels beyond the app (email/push) — email needs SMTP config and a decision about daily digest vs. event-driven.

How this was determined. Every claim above was read from the checked working tree (release/v2 at afafc60 plus uncommitted modifications): server routes/tools/model config, shared schema, client pages and components, and the existing SPEC/TODOS. npm run check exits clean and all 23 tests pass. No live deployment was exercised; model availability remains unverified.
